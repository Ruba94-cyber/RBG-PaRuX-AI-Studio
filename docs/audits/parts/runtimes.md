# Runtime and engine management: clean-room audit part

Domain key: `runtimes`. Date: 2026-10-19. Status: audit input, not committed.

## 1. Scope

- In scope: how each app obtains, installs, verifies, versions, pins, launches, stops, health-checks, updates, repairs and isolates inference engines (llama.cpp, Ollama, LM Studio, ExLlamaV3, ComfyUI), Python/PyTorch/CUDA environments, native dependencies, GPU backend choice, ports, logs, process ownership, update and rollback.
- LU side: Locally Uncensored v3.0.6 (AGPL-3.0), read-only clone outside the PaRuX repository. LU paths below are relative to that clone root (for example `src-tauri/src/commands/engine.rs`).
- PaRuX side: worktree `.claude/worktrees/parux-ci`, branch `feature/parux-competitive-integration-20261019`, HEAD `117fcf7`. PaRuX paths below are relative to the worktree root.
- Out of scope: model catalogs and model downloads (other parts), chat and tool protocol, voice, retrieval embeddings except where they share the runtime manager.

## 2. Method

- Static reading only. No LU script or binary was executed, no npm or cargo was run, no network was used, and no build or test was run in PaRuX.
- PaRuX C#: Serena symbol overviews and bodies first, then narrow ripgrep. LU Rust: narrow ripgrep for function signatures, endpoints and pins, then bounded reads of decisive ranges.
- Negative searches were run where a capability is claimed missing (garbled-output, sanity, SIGILL, 0xC000001D, AVX2 terms in `src/PaRuX.Server`; runtime download hosts in LU `src-tauri`).
- Test evidence means named test classes found under `tests/PaRuX.Server.Tests`. Tests were not run. `PARUX_EXECUTION_PLAN.md` and docs were used only as pointers to claimed real runs; the claims were not re-verified.
- Main-branch check: a `git ls-tree` comparison of runtime-related `src/` paths between `main` and `HEAD` found no runtime file that exists only on `main`. `onLocalMainOnly` is false for every row.
- Clean-room: behaviour is described in this audit's own words. LU identifiers, file names, flags and pinned identifiers are cited for traceability only. No LU code or long strings are reproduced.

## 3. Evidence and vocabulary

- `paruxEvidenceLevel`: `static` (code read), `unit_tests` (named test class), `e2e_real` (real run recorded in docs, not re-run here), `none` (negative search only).
- `paruxStatus`: task vocabulary (implemented_working, implemented_unwired, partial, prototype, docs_only, missing, obsolete, duplicated, replace).
- Priority: P0 blocks the goal of an easy, managed, best-in-class local AI studio. No P0 was found in this domain.

## 4. Summary

PaRuX is ahead on the managed lifecycle: digest-gated and host-restricted installs of llama.cpp and ComfyUI with side-by-side tags, rollback, performance-gated promotion, identity-checked processes that never adopt foreign listeners, a managed ExLlamaV3 pack, and a VRAM-aware hot pool.

LU is ahead on failure handling and self-healing: a post-health output probe, CPU retry rungs, illegal-instruction diagnosis, candidate ports, pinned and verified installers and interpreters, and a PyTorch channel chosen from GPU capability. LU also installs and controls Ollama, LM Studio, ComfyUI and Python. PaRuX does not manage competitor engines, by design.

The P1 gaps are: no output sanity probe; launch tier chosen only from `nvidia-smi`; no CUDA-to-Vulkan fallback; fixed port 1234 that is also the LM Studio default; a hard-coded `cu128` PyTorch index; and archive digests that come from the same GitHub channel as the asset.

## 6. Top 10 prioritised proposals

1. **Post-health output sanity probe** (row 9, P1). After `/health` is ok, send one fixed short prompt to 127.0.0.1 with a hard budget. Judge the reply for text-likeness (not empty, not one repeated character or token, mostly printable). On failure, restart once on the Vulkan build, then report an honest error. Hook: `StartTextAsync` / `LaunchAndWaitAsync`. Done when a unit test feeds garbage and good samples, and a real run shows the rung.
2. **One GPU-tier source of truth** (rows 7 and 21, P1). Decide the launch tier from the same inventory the hardware-fit path uses, with `nvidia-smi` kept only as the CUDA-specific signal. Add tests for an AMD card with large DXGI-reported VRAM and for a card that reports no VRAM.
3. **Launch fallback ladder** (row 8, P1). On a CUDA launch failure, retry once on the Vulkan build with the same model, then fail with both causes. Keep the existing stderr tail. Test with an injected launch failure.
4. **Port selection with clear conflict** (row 11, P1). Make the text port configurable with an ordered candidate list starting above the LM Studio default. When 1234 is held by a foreign listener, choose the next free candidate and say so. Keep `ManagedListenerOwnership` semantics.
5. **Channel-selected PyTorch index** (row 18, P1). One selection function shared by ExLlamaV3, Speech, Threed, TrainingLab, Avatar and Diffusers: NVIDIA compute capability to a channel with a fallback; AMD path; CPU path. Replace the five literal `cu128` sites (`ExLlamaV3BuildCatalog.cs:18`, `SpeechService.cs:67`, `ThreedService.cs:58`, `TrainingLabService.cs:349`, `AvatarEngineService.cs:64`) and route the two constant consumers (`ExLlamaV3ManagedPackService.cs:146`, `ManagedDiffusersImageEngine.cs:109`) through the new function. Unit-test the decision table.
6. **Download trust hardening** (row 2, P1). Add optional compiled-in SHA-256 pins for recommended llama.cpp tags and ComfyUI portables, and Authenticode verification of extracted `llama-server.exe` before activation. Record the verified digest in the install status.
7. **Illegal-instruction diagnosis** (row 10, P2). Classify SIGILL and Windows illegal-instruction exits; report detected CPU features and suggest the Vulkan or CPU build; retry once automatically on the CPU-capable build.
8. **Idempotence on the effective launch arguments** (row 13, P2). Compare a hash of the final argument list, including context, KV type and fit flags, rather than the profile label or model path alone. Restart on any difference.
9. **Durable install jobs and resumable downloads** (row 3, P2). Persist job state under the runtime root so progress survives restart; resume a partial archive with a byte range when the host supports it; keep the digest check on the full file.
10. **Unified runtime update view and error taxonomy** (row 22, P2). One list across llama.cpp tags, ComfyUI variants, ExLlamaV3 packs and uv, with ownership, rollback and update actions; distinguish GitHub rate-limit and network errors from install errors.

## 7. Do not copy from LU

- Killing whatever process listens on a port after a button press (`process.rs:1217-1260`). PaRuX must keep identity-checked ownership.
- Installer execution with size and signature checks only and no pinned digest (`install/ollama.rs:175`). Silent installers for competitor products (`install/ollama.rs:183`) conflict with the rule against mutating USER_MANAGED software.
- Binary download from a "latest" release URL with no verified digest in the code read (`src-tauri/src/commands/remote.rs` about `:3139-3143`). This was not confirmed either way; treat it as an anti-pattern until checked.

## 8. Risks

- Port 1234 is the LM Studio default. Users who run LM Studio will hit a failed start (likely).
- Digests come from the same GitHub channel as the asset. A compromised release yields matching digests. Trust rests on GitHub, not on a PaRuX-controlled pin.
- Unauthenticated GitHub API limits can break installs and the Update Manager on shared networks. There is no cache, and no token handling exists (and none should be added casually).
- AMD and Intel users get the 4B model regardless of VRAM because the tier uses `nvidia-smi` only.
- `cu128` wheels on unsupported or older GPUs, and on AMD machines, can produce Python features that fail at import.
- No CUDA-failure fallback means a failed CUDA start can leave the user without chat even when a working Vulkan build is installed.
- Regression-guard decisions rest on one representative model and one probe. Noise can promote a slower build or reject a faster one. Needs a repeatability criterion.
- Tests here are fake-HTTP and unit level. Real GitHub download, real GPU and real install paths need a recorded live run before any row can be called DONE under the project's Definition of Done.
- Clean-room: LU is AGPL-3.0. Implementers must receive only this specification, never LU source.

Which contract is canonical for USER_MANAGED backends? `ManagedListenerOwnership.cs:26-28` says user-managed backends are supported through `ExternalTextProviderService`. `ExternalTextProviderService.cs:14-18` says it is no longer an inference provider and the configured-endpoint getter always returns null. Confirm the current path.
- Q2. Is there a recorded live run of the full install pipeline (download, verify, extract, swap, activate) on the target PC? Only unit tests and plan notes were found.
- Q3. Does the App gate installs while a text model is resident, or only the server (`EnsureBackendIdle`)? App-side gating was not verified.
- Q4. Does `StartTextAsync` restart when the context or KV-cache preference changes while model path and profile label stay the same? Needs a targeted test.
- Q5. Long-path handling for runtime tag folders under the local-AI root. LU has explicit Windows long-path logic (`engine.rs` about `:1354-1642`); PaRuX status not verified.
- Q6. Product intent for Ollama and LM Studio: detect-only (current) or managed install (LU style)?
- Q7. Is the remote-access helper download in LU digest-checked? Not confirmed; not in scope for this domain beyond the anti-pattern note.

## 10. Not verified in this audit

- No LU run. LU behaviour is from source reading of v3.0.6 only.
- App-side flows (RuntimeManagerView, UpdateManagerView, OnboardingView) were checked only for calls into the runtime client, not for interaction behaviour.
- Serena could not confirm call sites for every race and engine class; wiring claims above name the call sites that were read.
