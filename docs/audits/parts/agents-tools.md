## 3. The 2026-09-21 external-target failure: documented, then what changed

Documented (plan lines 52-116): on 2026-09-21 the coding agent, driven through `/code` on an external .NET repository (9 projects, 83 `.cs` files), ran 82 steps and 2 repairs over about 35 minutes. It ended `status=failed`, no diff, and the target `dotnet build` and `dotnet test` were never reached. Measured root cause: the agent re-read the same 154-line file until its repeat guard and exploration budget blocked every other read, so it never issued an edit. The usable per-request window was 8,192 tokens because the runtime launched with `--ctx-size 32768 --parallel 4`, and llama.cpp splits context across slots.

Changed in code (verified by reading; unit tests named):

- Per-request window honoured by reducing slots, not by enlarging the cache (plan 160-178; `RuntimePerRequestContextTests`, `RuntimeLaunchOptimizerParallelTests`).
- Working memory scales with the observed window instead of a fixed 2,500 characters: `src/PaRuX.App/Services/CodingAgentPromptBudgetPolicy.cs`; `tests/PaRuX.Server.Tests/CodingAgentRecentEvidenceBudgetTests.cs:17`.
- Durable per-task memory on Core's Virtual Context ledger, wired at `src/PaRuX.App/Services/CodingAgentService.cs:378, 671, 865`; client at `src/PaRuX.App/Services/CodingTaskMemoryClient.cs:30`; tests `tests/PaRuX.Server.Tests/CodingTaskMemoryTests.cs:17`.
- Exact-match patch rejection replaced by ordered tolerant matching that refuses ambiguity: `src/PaRuX.App/Services/CodingAgentTools.cs:97-157`; `tests/PaRuX.Server.Tests/ReplaceRangeToleranceTests.cs` (9 `[Fact]`, lines 28-138).

Not closed:

- No external-target run after these changes is recorded. The plan still lists the external target as MISSING (plan 91, 273).
- The 8,192-token resident configuration remains open. At that size the agent returned empty actions ("missing action", plan 266-271). The BIC-09 entry still lists "the 8192 context" and the repeat-task success rate as open (plan 2744-2746).
- A synthetic .NET target passed one edit, build and 8/8 tests on 2026-09-26 (plan 706-720). Status stays PARTIAL.

Verdict: the named defects were fixed in code and are unit-tested. The external-target acceptance has not been demonstrated, and the small-window regime is still open. The 2026-09-21 failure is fixed in code for its named causes, not closed as a real-run result.

## 5. Top 10 prioritised proposals

Each proposal is a behavioural spec for implementers. Implementers must not open the LU clone.

1. **P0 - Close the external-target acceptance (rows 20, 11).** Spec: on a real external .NET repository, run one directed task (named file, named change, one test, build and test) and one open-ended task through the current coding path. Test at resident windows of 8,192 and 16,384 tokens. Acceptance means a non-empty diff, a green build and test run recorded by the verifier, and the per-step time. Record evidence in the plan and update status only from that record.
2. **P0 - Make an 8k resident window usable (rows 11, 2).** Spec: reserve an answer budget before any evidence is added. Cap the fixed system prompt and the repository-evidence share to fit what is left. On an empty or unparseable model output, retry at most once with a compacted prompt, then stop with an honest status. Accept fenced JSON and minor near-JSON defects through one tolerant parse step before counting a protocol failure.
3. **P1 - Epoch-scoped repeat detection (row 7).** Spec: an identical read call is allowed once per workspace epoch. On the second identical call, steer the model once. On the third, halt the run with a clear reason. Any successful mutation starts a new epoch. Keep the existing count-based watchdog as the backstop.
4. **P1 - Gate direct `/code` completions (row 8).** Spec: a direct run's completion is accepted only when a deterministic verification receipt is bound to the current workspace fingerprint, or an independent verifier approves it. Keep the checkpoint until that happens. Bind receipts to the fingerprint so a worker cannot reuse an old receipt.
5. **P1 - Ask and Plan modes for coding runs (row 5).** Spec: Ask pauses before any arbitrary command and before staged writes, and shows the exact command. Plan is read-only: no write actions, and commands must pass a read-only classifier that refuses chaining, substitution and redirection. Both sit on top of the existing sandbox and preflight. The sandbox remains the boundary.
6. **P1 - Sensitive-action gate for computer use (row 12).** Spec: before any action that sends, buys, deletes or changes permissions, or any click on an unnamed target, or any typing when focus cannot be verified, require a fresh on-screen confirmation. Keep a fixed never-touch list: terminals, password managers, system sign-in and security settings, admin windows, and the app's own window. Do not capture the screen while a password field has focus. Treat text read from the screen as untrusted.
7. **P1 - Threat review of remote approve-once (row 19).** Spec: a paired device may approve one computer-use action only if the desktop shows the same action and a hash of it, the approval is bound to that action, and it expires quickly. Add per-capability switches for remote agent use, default off.
8. **P1 - Validate the Windows sandbox on an elevated gate (row 6).** Spec: run the AppContainer integration tests on an elevated physical-PC gate and record the result. Keep the fail-closed behaviour: if the container cannot be created, the command does not run.
9. **P2 - MCP name-collision refusal and coding-agent access (row 14).** Spec: an external MCP tool whose name matches a built-in is refused, never merged or suffixed. Expose MCP tools to coding runs only through the same permission policy as built-ins.
10. **P2 - Real-run evidence for browser automation and a decision on workflow steps (rows 13, 18).** Spec: one recorded run of the CDP tools against a local web app, with the private profile. Decide whether workflows gain prompt, condition, loop and user-input steps, or stay as task graphs. Document the decision.

## 6. Risks

- Sandbox evidence is conditional: the AppContainer integration tests fail under a non-elevated split token on the workstation (plan 2527-2529).
- Tolerant patch matching can apply an edit to a unique but wrong region. Refusal on ambiguity limits this, but no near-duplicate-block test was found.
- Remote approve-once extends the attack surface to paired devices (row 19).
- The 8k regime can return empty output for a long time before any stop. The 60-step watchdog took about 35 minutes in the 2026-09-21 run.
- Serena's index for this worktree is stale. Maintainers using it will get wrong line numbers until it is refreshed.
- Clean-room discipline: LU is AGPL-3.0 and PaRuX is MIT. Implementers receive only the specs above.
- LU's stall heuristics are regular-expression verdicts. Copy the behaviour, not the patterns.
- Residual TOCTOU window in the filesystem apply path (`ShadowApplyTransaction.cs:460-466`).
